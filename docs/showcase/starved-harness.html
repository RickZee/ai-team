The Starved Harness

I built an eval system that implements the error-analysis methodology correctly, in about thirteen thousand lines. Then I audited it against the methodology it cites and found that every stage downstream of "look at your data" has never seen any data. This is what the audit found, and what the numbers are actually worth.

Built everywhere, fed nowhere

the loop, stage by stage

The methodology is not in dispute. Traces before scores. Binary verdicts, never Likert. True-positive and true-negative rates, never accuracy alone. A single domain expert as annotator. Open coding that deliberately refuses to show the annotator a model's guess, because a model-labelled ground truth makes every number downstream meaningless.

All seven stages are implemented. The top bar is how much of the stage exists in code. The bottom bar is how much real data has ever passed through it.

Fifty traces from one backend, one scenario, one status, produced inside a two-second batch is n=1 wearing n=50's clothes — and the last row is the part that stings: the runs that would clear four of these five floors were already on disk, in a directory the corpus builder never opened. Every floor is unmet, so anything derived from this corpus renders with a NON-REPRESENTATIVE stamp — emitted by the report renderer, where prose cannot opt out of it.

Root cause, in two parts

neither of them in the eval code

One: the corpus reads the wrong tree. The backfill command defaults to --workspace-root ./workspace — the directory where the agents' generated code lands. The harness's own run records go somewhere else, and have been accumulating there since July.

Backends recorded in that unread tree: langgraph 148, crewai 1, claude-agent-sdk 1, unset 60 — spanning 6 July to 13 September, 69 days. The corpus that indexed as one backend over 1.97 seconds could have been three backends over sixty-nine days, for $0.00, on the day that line was written. Four of the five diversity floors were reachable from disk the entire time.

Two: phase telemetry is asked for, not written. phases.jsonl yields the phase and retry spans every trajectory check reasons over. Its only writer in code is a harness module added last week, which appends a single row when it records context pressure. Otherwise:

src/ai_team/backends/claude_agent_sdk_backend/agents/prompts.py:23

   (JSON lines: phase, status, timestamp).

Zero such files exist — not under workspace/, not under output/runs/, not in 440 runs.

Worth being precise, because the general version of this claim would be false and the specific version is more useful: most of the telemetry here is written by code. audit.jsonl has a writer in the tool bus. costs.jsonl has two, and sixty of them exist on disk. Phase records are the one signal left to an instruction — and the one every trajectory check depends on.

Where the taxonomy came from

17 failure modes by origin
Essay, written from memory 13 External reference 4 Observed in a trace 0

Thirteen failure modes came from an essay I wrote in July from memory. Four came from published Anthropic references. None came from reading a trace. Every deterministic check in the harness is bound to one of these seventeen, which means the checks are well-engineered detectors for failures nobody has confirmed the system has.

The fix is a field, not an argument: each mode now records origin — essay, reference, hypothesis or open_coding — and open_coding requires annotation ids behind it. Promotion takes evidence. It makes today's state legible in one line, and uncomfortable to look at until it changes.

What a green check is worth

corpus kind, rendered on every rate
Three kinds of pass rate, and which one this repo can currently produce
Kind Source What a pass rate means Today
FIXTURE-ONLY 94 synthetic pass/fail/na fixtures across 21 checks the check code behaves as written available
CORPUS indexed traces from real runs the system behaved this way on this sample no corpus
LIVE a budgeted tier run just executed the system behaves this way now unspent

The per-PR eval job in CI is real, costs $0.00, and runs on every pull request. It replays fixtures. A green result proves the check code behaves as written and has never once said anything about whether the agents work. The repo already disclosed this, in a README — and then let the numbers travel without the disclosure attached. Rendering the corpus kind beside every rate is what stops a fixture pass rate from arriving in a conference talk as a quality claim.

The remediation

16 requirements · 9 phases · 47 tasks
Task 2.4

Read the tree the records are in

One argument, $0.00, and the highest-value task in the spec: ~210 traces, three backends, a 69-day span, with backend and status taken from run records instead of guessed from directory names. --workspace-root survives as a secondary source for runs with no record.

Phase 1

Phase telemetry becomes harness-owned

A single writer on the execution path, constructed by the backend wrapper so a new backend inherits it, writing beside run.json rather than into a tree nobody reads. Every record stamped writer: harness by the module, so no call site can forge it. The prompt line is deleted, not supplemented — leaving it gives one file two writers and makes provenance unresolvable exactly when it matters.

FM-018

Self-reported telemetry becomes a failure mode

A run whose records were written by the model rather than the harness. Deterministic, $0.00, scoreable retroactively — it marks all 50 existing traces, and that is recorded as a baseline, not a regression. Its sibling FM-016 catches an agent grading its own work; FM-018 catches an agent reporting its own work, which is worse, because it yields a clean-looking dataset nothing downstream can question.

Phase 2

Unreadable is not failed

A new unindexable trace state, excluded from every numerator and denominator and counted separately. Absence of evidence stops being recorded as evidence of failure. Then a diversity floor with a stamp the renderer enforces.

Phase 4

One hundred traces, read by a person

Thirty unaided first, then to saturation — defined operationally as twenty consecutive traces producing no new tag. Axial coding into five to eight categories, counted, with Wilson intervals and the sample stamped on the table.

Human-only · an agent reading the task list must stop here and say so
Guards

Three refusals with no override flag

Axial clustering refuses under 30 unaided annotations. Judge validation refuses under 100 human labels. The re-run resolver refuses above its ceiling. The loop was skippable because nothing refused — and a flag is how a refusal becomes a formality.

The rules this page follows

claim discipline

What may be published from a starved harness

  1. Every rate carries its corpus kind and its n. A rate without n is a defect in the claim, not a rounding of it.
  2. “$0 per-PR eval gate in CI” is publishable. “Our agents pass 94% of evals” is not, in any phrasing, until a CORPUS rate exists.
  3. The gap is the story. Describing the harness as finished and fed would be a worse claim than describing it as built and starving — and the second one is the interesting half.

The smallest version of the fix is one free command and one unavoidable afternoon: re-index the right directory, then read thirty traces yourself. That will change what you build next more than the remaining eight phases combined — which is, stripped of everything else, the entire content of the podcast that started this.
